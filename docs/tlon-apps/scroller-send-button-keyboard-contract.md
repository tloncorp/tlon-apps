# Composer Send keyboard access

Declared against preserved actual-app keyboard failures, before the proposed fix or rerun. Existing accepted keyboard contract requires Tab from the composer to Send without submitting, Shift+Tab to return with the exact draft and selection, and normal keyboard activation of the user-visible control. The current custom Button renders a generic div; its web event adapter supplies onClick but no native button keyboard behavior. Do not replace Tab with programmatic focus or permit a different target merely to pass.

Proposed bounded fix: render the existing Send action as a native HTML button on web with an explicit accessible name. Keep existing onPress, disabled, loading, edit/retry routing and visual sizing. The native control receives the appropriate button semantics/name without a new wrapper. Verify the actual rendered element, browser Tab/Shift+Tab behavior, disabled behavior and one real send via Enter and Space in the normal app, with exact backend text/id/author and preserved scroller state. A JSX prop test alone cannot qualify this behavior. Inspect the actual DOM/form relationship and button default action; this app currently has no composer form, but do not claim form-submission semantics from the proposal.

Preserve the existing full keyboard sequences, deadlines, failures and 1px geometry bounds. Their input/selection/focus verdicts stay distinct from transient sampled geometry and presented-frame evidence. No source edit or browser run has happened from this proposal while the full42 snapshot is frozen.

The two new functional browser cases run in playwright.scroller-interaction.config.ts and the ordinary web E2E suite. They validate button semantics, trusted activation, one real request, exact durable message and a quiet tail. They do not independently qualify continuous geometry, input latency, caret or presented frames; the existing strict keyboard sequences retain those separate checks.

Implementation after the full42 capture: use the installed Tamagui `render` API with `<button type="button" />` on web, preserving the same action component. The explicit type prevents implicit form submission. The browser assertions require the actual BUTTON tag, type, disabled property and accessible name; no cast or prop-only test substitutes for those observations. Runtime validation remains pending.

The first functional run exposed that this custom-render path forwards React Native accessibility props as unknown HTML attributes. The corrected element supplies native HTML `aria-label` and `disabled` directly; native platforms retain their accessibility props. The unchanged Enter and Space cases both pass in the actual app, with one exact backend message each. Both attempts and their source snapshots are retained; see the refactor result ledger.
